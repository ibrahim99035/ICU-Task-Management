01

The one-minute explanation

Use this as the opening answer before walking through screens or scenarios.

What TaskLog does

TaskLog is a thesis demo for nurses working in dynamic care units. It helps a nurse plan a shift by task priority, time care from stored timestamps, protect tier 1–2 work during an emergency, and build a handover from what actually happened.

A head nurse creates units and assigns nurses. The nurse starts a shift inside one unit. Every task created in that shift belongs to the same unit, so the head nurse can filter shifts, analytics and exports by unit. Both roles can correct an unfinished task and add a note; the change is appended to the event log.

The six points to say out loud

  1. Two roles: nurse and head nurse. There is no admin role, no doctor role and no patient account.
  2. Dynamic units: units are not hard-coded. A head nurse creates them and assigns nurses.
  3. Offline-first nurse: actions are written to the device first, then synced.
  4. Rule-based: no AI or machine learning. Tier 1–2 work is never auto-deferred.
  5. No score: the head nurse writes five separate 1–5 ratings; the app never averages or ranks nurses.
  6. No identifiers: bed number plus a short nickname only. No names, MRNs, dates of birth or photos.
The shortest correct answer: “TaskLog is an offline-first, rule-based task planner and handover aid for nurses. A head nurse configures units and reviews finished shifts; a nurse works the shift inside one assigned unit. It records timestamps and events, not clinical decisions or performance scores.”
02

The roles at a glance

The application has exactly two authenticated roles. The unauthenticated visitor is an entry state, not a third role. Head-nurse accounts are provisioned; public signup creates nurse accounts only.

?
Entry state

Visitor / unauthenticated

Someone who opens the link but has not signed in.

  • Can: read the login and disclaimer, create a nurse account, or resume a saved offline session.
  • Cannot: see shifts, units, tasks, reviews or exports.
  • Lands on: /login; the root route redirects there.
N
nurse

Nurse

The person working the shift and logging care.

  • Can: start/end a shift in an assigned unit, manage tasks, edit unfinished task details, write a note on an unfinished task, log interruptions, handle emergencies, reschedule tier 3–4 work, finalize handover, read own summary and reviews, complete surveys.
  • Cannot: create units, assign nurses, see other nurses’ shifts, rate anyone, export unit data, or alter a completed/missed task.
  • Lands on: /beds when a shift is active; otherwise /shift-start.
H
head_nurse

Head nurse

The person who configures units, reviews shifts and can correct unfinished tasks.

  • Can: create/archive units, assign nurses, filter dashboard/shifts/exports by unit, inspect shift timelines, edit unfinished task details, write a note on an unfinished task, write five manual ratings, export CSV.
  • Cannot: run the nurse shift flow, start, pause, complete or end a nurse’s task, alter a completed/missed task, log interruptions, finalize a handover, or rewrite the event log.
  • Lands on: /head.
Important distinction The head nurse is not a “super nurse” inside the same screens. The head-nurse screens are analysis, unit configuration and manual review, plus a narrow correction path for unfinished tasks. The nurse flow is a separate, offline-first workspace.

04

Visitor / unauthenticated flow

The visitor is not a product role, but it is the first state every participant sees.

1Open linkRoot route checks for a saved session.
2Login screenSign in or create a nurse account.
3Choose pathOnline login, registration, or resume offline.
4Role routingHead → dashboard; nurse → shift start/beds.

What the visitor sees

  • Product name and the “planning, timing & handover aid” positioning.
  • The disclaimer: not a medical device; practice data only.
  • Login fields: username and PIN.
  • A “Create account” tab for a nurse account.
  • A “Continue offline” option if a session was previously saved on that device.

What the visitor cannot do

  • Browse units, shifts, tasks, handovers, reviews or exports.
  • Create a head-nurse account from the public form.
  • Choose a role in the request; the server rejects role injection.
  • Recover a PIN by email; there is no email or recovery flow in this demo.
Explain it this way “A visitor can only create a nurse account or sign in. Head-nurse accounts are provisioned by the study team. The server never trusts a role sent by the browser.”
05

Nurse role

The nurse is the main operational user. The nurse flow is designed to keep working when the network is unreliable.

Purpose of the role

The nurse plans and logs the shift: choose an assigned unit, start with demo beds, work the tier-sorted queue, edit unfinished tasks and add notes, record interruptions and emergencies, confirm new times for deferred work, finalize a handover, and end the shift.

Beds Tasks Handover Me

Role boundary

  • Sees: own active shift, own beds, own tasks, own handovers, own summary, own reviews.
  • Can alter: unfinished task details and notes in the nurse’s own shift only. Completed and missed tasks are frozen.
  • Does not see: other nurses’ shifts, unit-wide analytics, export screens, unit management.
  • Offline: the nurse flow is the only flow that is designed to continue offline.
  • Routing: if no shift is active, nurse screens redirect to /shift-start.
Unit assignment is a precondition A nurse must be assigned to at least one active unit before a shift can start. If no active unit is cached or returned, the shift-start screen shows “No assigned unit” and disables the start button.

Nurse screen map

/shift-start · Start a shift

Choose unit, shift type and demo beds. Backdate by two hours for a demo.

/beds · Bed overview

Bed cards, task counts, emergencies, shift clock and end-shift action.

/tasks · Task queue

Tier-sorted work, filters, timers, quick add, edit/note on unfinished tasks, interruption logging.

/review-deferred · Confirm new times

After an emergency, confirm suggested times for tier 3–4 tasks.

/handover · Handover

Generate a snapshot from the event log, add a note and finalize.

/summary · Shift summary

Timestamp-derived totals, completion, tier facts and review status.

06

Nurse scenarios and flows

Each scenario lists the trigger, the steps, the result and the rule that makes it defensible.

N1 Create a nurse accountFirst-time participant; no account exists. ›
  1. Open /login and choose Create account.
  2. Enter a unique username, display name, PIN and confirmation PIN.
  3. The server hashes the PIN with bcrypt and creates only a nurse account.
  4. A participant code such as N-... is generated for analysis.
  5. The app signs the nurse in and sends them to /shift-start.
Result: a nurse account exists, the role is forced server-side, and the account can start a shift after the head nurse assigns it to a unit.
Rule: public signup never creates a head nurse. A client-supplied role is rejected. Duplicate usernames return an error.
N2 Sign in or resume offlineReturning nurse; network may or may not be available. ›
  1. Online: enter username and PIN at /login. The API returns a token and the user record.
  2. The app stores the auth record locally so the session can be resumed.
  3. Head nurse → /head; nurse → /beds.
  4. If the nurse has no active shift, /beds redirects to /shift-start.
  5. Offline: choose Continue offline. The saved session is resumed from the device.
Result: the nurse can return to the local shift and continue logging without the server.
Rule: offline resume is a nurse convenience, not a bypass of role rules. The device still has only that nurse’s local data.
N3 Start a shift inside an assigned unitNurse is assigned to one or more active units. ›
  1. Open /shift-start.
  2. Choose an assigned active unit from the Unit card. The assigned units come from the cache and are refreshed from the API when online.
  3. Choose shift type: Day, Night or Custom.
  4. Choose the demo beds. The default is all six beds with their preset tasks.
  5. Optionally keep Demo: start 2 hours ago to make overdue and tier-ordering states visible immediately.
  6. Tap Start day shift · [unit] · 6 beds · 41 tasks.
Result: a local shift row is created with unitId and unitName; beds, preset tasks and a SHIFT_STARTED event are written to Dexie first.
Rule: one shift has exactly one unit. If no unit is selected, the start button is disabled. Tasks created in the shift inherit that unit.
N4 Work the tier-sorted task queueShift is active; the nurse needs to see what matters first. ›
  1. Open /tasks. The queue is sorted by tier, then time window.
  2. Use the filters Open, Overdue, Deferred and Done.
  3. Open a bed from /beds to filter the queue to that bed.
  4. Press play to start a task; press pause to stop the timer; press resume to continue; press done to finish.
  5. Pin a task if it must stay visible at the top.
Result: each action appends an event. The task status and elapsed time are computed from the event log, not from an in-memory counter.
Rule: durations come from stored timestamps. A task marked done without a timer records completion but no duration.
N5 Correct a timestampThe nurse tapped the wrong time; the original must remain auditable. ›
  1. Open the task detail sheet.
  2. Find the stored event for start, pause, resume or completion.
  3. Edit the displayed time and save the correction.
  4. The app writes a correction event; the original event is not deleted.
Result: the projection uses the corrected time while the event history still shows what happened.
Rule: corrections are additive. The log is the evidence, not a mutable “current value” only.
N6 Quick-add a taskA new task appears that was not in the preset list. ›
  1. On /tasks, tap the plus button.
  2. Choose the bed.
  3. Pick a preset: repositioning, oral care, vital signs, charting, supplies or family update.
  4. Or expand Custom task and enter title, tier, category and expected minutes.
  5. Confirm. The task is added to the current shift and unit.
Result: the new task appears in the queue and follows the same timer, tier and handover rules.
Rule: quick add is a local-first action. It is queued for sync like every other event.
N7 Edit a task and write a noteThe task needs a clearer title, a new tier or time, or context for the next nurse. ›
  1. Open an unfinished task from /tasks and choose Edit / note.
  2. Change the title, tier, category, planned start/end or expected minutes.
  3. Write a short note for the next nurse. Do not enter names, MRNs or other patient identifiers.
  4. Save. The task updates and a TASK_EDITED event is appended; the earlier events stay in the log.
Result: the task queue, task detail, head-nurse task list and a later handover snapshot use the edited values. The note is visible on the task and in the handover.
Rule: only planned, in-progress, paused or deferred tasks can be altered. Done and missed tasks are frozen so the historical record stays stable.
N8 Log an interruption Care is interrupted by a physician request, missing equipment, family/visitor, other staff or another reason. ›
  1. From the task queue, open Interruption; or open the active task bar and choose interrupt.
  2. Choose the affected bed/task if relevant.
  3. Choose a reason.
  4. Record the start and end time.
  5. Optionally pause the active task; resume it when work continues.
Result: an interruption event is stored with its reason and duration. The head dashboard can show top reasons and total minutes.
Rule: interruption time is recorded, not guessed. It is displayed separately from direct care.
N9 Start and end an emergencyA bed needs immediate attention and the nurse must protect critical work. ›
  1. On /beds, choose Emergency on this bed.
  2. Confirm. The emergency is active and the banner appears.
  3. Tier 1–2 tasks on that bed are flagged with needs attention and stay visible.
  4. When the emergency ends, choose End emergency & review deferrals.
  5. The app suggests new times for tier 3–4 tasks using the actual emergency duration.
  6. Review each proposal, edit the time if needed, and confirm one or all.
Result: emergency minutes are recorded, tier 1–2 work was never deferred, and only tier 3–4 work receives a new time after confirmation.
Rule: this is the core safety rule. The app never automatically defers tier 1–2 tasks. Nothing moves until the nurse confirms the new time.
N10 Finalize a handoverThe nurse needs a shift handover built from what actually happened. ›
  1. Open /handover.
  2. Choose a bed.
  3. Review the snapshot: done, pending, deferred and missed tasks; interruptions; emergency minutes.
  4. Add a free-text note. The UI warns against names and identifiers.
  5. Tap Finalize handover and confirm.
  6. Copy, share or print the generated handover text.
Result: a frozen handover snapshot is written to the event log. A later edit cannot overwrite it.
Rule: the handover is generated from stored events, not typed from memory. The snapshot is immutable after finalization.
N11 End the shift and read the summaryCare is complete; the nurse wants a timestamp-based record.
  1. On /beds, choose End this shift.
  2. Confirm the end-shift dialog.
  3. Open tasks are marked missed with the reason shift_end.
  4. The summary is frozen and opened at /summary.
  5. Read direct care, indirect care, interruption and emergency minutes; completion; tier 1–2 on-time rate; missed/deferred counts.
  6. If a head-nurse review exists, the nurse can read the manual ratings on the summary or in /me.
Result: the shift is closed, the summary becomes stable, and the data is available for sync and head-nurse review.
Rule: the summary is computed from timestamps. It is not a performance score and does not rank the nurse.
N12 Surveys, privacy and sign-outThe participant finishes or wants to understand the data. ›
  1. Open /me for profile, active shift, local history, reviews and tool links.
  2. Open Evaluation surveys to complete SUS and raw NASA-TLX forms. Answers use the participant code, not a patient identifier.
  3. Open Privacy & data to read what is stored and what is not.
  4. Sign out. The confirmation explains that local events, tasks, handovers, shifts and beds are removed from this browser; synced server copies remain.
Result: the participant can complete the evaluation instruments and understand the data boundary. Signing out clears the local device copy, including any unsynced outbox items, so the confirmation is a deliberate warning.
Rule: surveys are anonymous by participant code. Sign out clears local data, not server records; there is no self-service server deletion in this demo.
What the nurse cannot do The nurse cannot create units, assign other nurses, open the head dashboard, rate themselves or anyone else, inspect another nurse’s shifts, export the unit dataset, or alter a completed/missed task. A direct URL to a head-nurse screen redirects, and the API also rejects the request.
07

Head nurse role

The head nurse configures the organisational layer, reviews the evidence, and can correct an unfinished task during or after a shift.

Purpose of the role

The head nurse creates units, assigns nurses, monitors unit-level facts, opens an individual shift to see what happened, can correct an unfinished task or add a note, writes five manual ratings, and exports CSV files for analysis.

Dashboard Units Shifts Export Me

Role boundary

  • Sees: all units, all nurses’ finished and open shifts, unit analytics, event timelines, reviews and exports.
  • Can alter: unfinished task details and notes from a shift detail, including shifts that are still open. Every change is appended as an event with the head nurse as actor.
  • Does not see: a full “super nurse” workspace. The head nurse cannot start, pause, complete, miss, defer or reschedule a task, log interruptions, finalize handovers, or edit completed/missed tasks.
  • Offline: head-nurse screens require a connection. Nurse logging remains offline on the nurse device.
  • Routing: if a nurse opens a head URL, the app redirects to /beds.
The unit model A nurse can belong to more than one unit. A shift belongs to exactly one unit. Tasks inherit the shift unit. Any head nurse in this demo can manage all units; created_by is retained for audit.

Head-nurse screen map

/head · Unit dashboard

Unit-filtered averages, time split, interruption reasons, review queue and recent shifts.

/head/units · Units

Create, rename, archive/restore, delete unused units, assign nurses.

/head/shifts · Nurse shifts

Date, unit and nurse filters; search; review status.

/head/shift · Shift detail

Summary facts, task list with edit/note on unfinished tasks, interruptions, emergency timeline and event log.

/head/review · Manual review

Five separate 1–5 ratings, comment, support flag; no composite score.

/head/export · Export data

CSV for events, summaries, surveys or reviews, optionally filtered by unit.

Head-nurse scenarios and flows

These are the scenarios to demonstrate when explaining the management and review side.

H1 Sign in to the unit dashboardHead-nurse account is provisioned. ›
  1. Open /login and sign in with the head-nurse account.
  2. The app routes to /head.
  3. Choose 7d, 30d or 90d.
  4. Choose All units, a specific unit, or Unassigned.
  5. Read unit-level averages: direct care, indirect care, interruptions, emergency time; completion and tier 1–2 on-time rate; missed and deferred totals.
Result: the dashboard shows unit-level activity facts for finished shifts. It does not rank nurses.
Rule: the dashboard needs a connection. The head nurse does not write clinical data here.
H2 Create a unitA new care area needs its own grouping. ›
  1. Open Units in the head navigation.
  2. Enter a unit name and optional description under Create unit.
  3. Tap Create unit.
  4. The unit appears in the unit list with status active.
Result: the unit can now be assigned to nurses and selected at shift start.
Rule: unit names are unique (case-insensitive) and descriptions are short. No patient identifiers are allowed in the description.
H3 Assign nurses to a unitThe unit exists; the head nurse must decide who works in it. ›
  1. Select a unit from the unit list.
  2. Search the nurse list by name, username or participant code.
  3. Tick one or more nurses. A nurse can be ticked in more than one unit.
  4. Tap Save assignments.
  5. The change is written to unit_nurses and appears in the selected count.
Result: the assigned nurse sees the active unit at shift start and in offline cache after the next sync.
Rule: only accounts with the nurse role can be assigned. Removing a nurse does not rewrite past shifts, because those shifts store their own unit_id.
H4 Archive, restore or delete a unitA unit is no longer used, or was created by mistake. ›
  1. Select the unit.
  2. Choose Archive to hide it from online shift choices while keeping history.
  3. Choose Restore to make it active again.
  4. Choose Delete unused only if the unit has no shifts.
Result: archived units disappear from assigned active lists; historical shifts remain readable. A unit with shifts cannot be deleted.
Rule: archiving is safer than deleting. Historical data is preserved. Queued offline shifts still sync if the unit exists, so work is not lost.
H5 Find a shiftThe head nurse needs one nurse’s shift within a date range. ›
  1. Open Shifts.
  2. Set From and To dates.
  3. Filter by unit: all, a specific unit, or unassigned.
  4. Filter by nurse.
  5. Search by nurse name, participant code, unit name or shift type.
  6. Read the row: nurse, unit, shift type, date/time, completion and review status.
Result: a filtered list of shifts; each row opens the shift detail or review action.
Rule: the head nurse sees all shifts, but the list is still a record of work, not a ranking.
H6 Inspect the shift detailThe head nurse wants to understand what happened. ›
  1. Open a shift from the list or dashboard.
  2. Check the header: nurse, participant code, unit, start/end time.
  3. Read the summary: direct care, indirect care, interruption, emergency, completion, tier 1–2 on-time, missed/deferred.
  4. Inspect tier breakdown, task list, interruptions and emergency timeline.
  5. Review the event log for the stored sequence.
Result: the head nurse can trace the shift from summary facts back to the event log and see which tasks are still editable.
Rule: the event log is append-only. The head nurse cannot rewrite or delete an event; editing an unfinished task adds a new TASK_EDITED event.
H7 Write a manual reviewThe shift is finished and needs feedback. ›
  1. Open a finished shift and choose Manual review.
  2. Rate five separate criteria from 1 (needs support) to 5 (strong): Task completion, Critical task timeliness, Interruption handling, Handover quality, Documentation.
  3. Write a behavioural comment; do not include patient identifiers.
  4. Optionally flag Needs support.
  5. Save. The nurse can read the ratings.
Result: five separate ratings are stored. The app does not average, weight or rank them.
Rule: no composite performance score and no leaderboard. “Needs support” is a support flag, not a ranking.
H8 Export CSV for analysisThe head nurse needs data for the thesis. ›
  1. Open Export.
  2. Choose a unit filter if needed.
  3. Choose one of four exports: Shift summaries, Event log, Survey responses or Reviews.
  4. Download the CSV.
Result: a CSV is downloaded with the selected unit and scope. Summaries, events and reviews include unit_id and unit_name.
Rule: no patient identifiers are exported. Survey exports use participant codes; reviews contain manual ratings, not a computed score.
H9 Edit an unfinished task or add a noteThe head nurse sees a task that needs a correction or context for the next nurse. ›
  1. Open a shift from the dashboard or Shifts list.
  2. Find the Tasks card in the shift detail.
  3. Tap the pencil on any unfinished task. Finished tasks show Locked.
  4. Change the title, tier, category, planned start/end or expected minutes, and/or write a short note.
  5. Save. The change is appended as a TASK_EDITED event with the head nurse as actor.
Result: the task list and timeline update immediately. The assigned nurse receives the new event on the next sync and the projection is rebuilt. A note also appears in a handover snapshot created after the edit.
Rule: the head nurse can alter only unfinished tasks. The head nurse cannot start, pause, complete, miss, defer or reschedule a task, or log an interruption. Completed and missed tasks stay frozen. If the nurse and head nurse edit the same task, the later event wins; there is no three-way merge in this demo.
What the head nurse cannot do The head nurse cannot start a nurse shift, start/pause/complete a task, log interruptions, finalize a nurse’s handover, alter a completed/missed task, or delete an event. The role stays configuration + review plus a narrow, audited correction path for unfinished tasks.

10

Offline and sync flow

This is the most important technical behaviour to explain after the role flow.

Online

  1. Nurse signs in; the API returns user, token and assigned active units.
  2. Units are cached in Dexie. Templates and config are also cached.
  3. Shift, beds, tasks and events are written locally first.
  4. The outbox pushes events to /api/sync/push.
  5. The server recomputes the shift summary and stores it.
  6. The head dashboard can read the finished shift after sync.

Offline

  1. The nurse can resume the saved session.
  2. The cached assigned units are available.
  3. Shift actions continue to write to Dexie.
  4. Events wait in the outbox; the sync chip shows pending work.
  5. No head dashboard, export or unit management offline.
  6. When the network returns, the outbox drains and the pull refreshes the cache.
1Local actionWrite event to Dexie.
2ProjectionUI updates from the event log.
3OutboxQueue the event for sync.
4ReconnectPush queued events.
5PullRefresh units, templates, shifts.
6Head viewServer summary becomes available.
Unit cache edge case If a unit is archived after the nurse cached it, an already-started offline shift can still sync as long as the unit row still exists. The server accepts the work instead of discarding it. Future shift-start choices refresh to active units only.
No patient identifiers Beds are a number plus a short nickname. The UI repeats the warning. The app cannot reliably detect a name typed into free text, so human input remains the boundary and this is listed as an evaluation risk.
11

Emergency and deferral flow

This is the safety-critical rule the thesis is built around.

1Emergency startsNurse confirms on a bed.
2Critical work flaggedTier 1–2 stays visible.
3Emergency endsDuration is stored.
4ProposalsTier 3–4 only; old time + duration.
5Nurse confirmsEdit and confirm each new time.
6AuditOld time remains in the event log.

Never deferred automatically

  • Tier 1 — immediate / life-critical.
  • Tier 2 — urgent, time-sensitive.
  • During an emergency they are flagged for attention, not moved out of the queue.

May be proposed for a new time

  • Tier 3 — scheduled care that can move.
  • Tier 4 — indirect or flexible work.
  • The suggested time is the old time plus the actual emergency duration.
  • The nurse can edit the time; nothing moves until confirmation.
Say this exactly: “Tier 1 and tier 2 are never deferred automatically. The app protects them and keeps them visible. Only planned tier 3–4 work receives a proposed new time after the emergency, and the nurse must confirm every change.”
12

Product rules to repeat in every explanation

These are the non-negotiable boundaries. They are also enforced by the product-rule lint where possible.

Two roles only

nurse and head_nurse. No admin, doctor or patient login.

No patient identifiers

No names, MRNs, IDs, dates of birth or photos. Bed number plus short nickname only.

Rule-based only

No AI or ML. No automatic clinical decision-making.

Tier 1–2 protection

Never auto-deferred. Only tier 3–4 can be proposed for a new time.

No score or ranking

Five manual ratings, no average, no weighting, no leaderboard.

Offline-first nurse

Every action is written to Dexie first and synced later.

Timestamps, not counters

Durations are computed from stored event times.

Visible disclaimer

Login, app shell and handover keep the “not a medical device” boundary visible.

Dynamic units

Units are configured by head nurses; they are not ICU-hard-coded.

Out of scope for this prototype EHR/order integration, biometric or OAuth login, push notifications, iOS, Arabic/RTL, admin screens, template editor UI, weighted TLX, TAM and AI.

Technical appendix

Enough architecture to answer follow-up questions without turning the explanation into a code review.

Stack

  • One Next.js App Router project at the repository root.
  • Hono API mounted inside /api/[[...route]].
  • Neon PostgreSQL + Drizzle ORM for server data.
  • Dexie for the local event log, outbox, tasks, shifts, handover and units cache.
  • Zustand for app state.
  • Capacitor 8.6 for the Android APK; the APK is a static export that calls the Vercel API.

Data model in one view

  • users — id, username, hashed PIN, role, display name, participant code.
  • units — id, name, description, status, created by, timestamps.
  • unit_nurses — unit + nurse membership, assigned by/at.
  • shifts — user, optional unit, type, start/end, summary.
  • events — append-only domain events; the source of truth for projections.
  • shift_reviews — five scores, comment, support flag, reviewer.
  • survey_responses — participant code, instrument, phase, score, answers.

Role enforcement

  • Client: navigation is role-specific; nurse screens redirect head nurses and vice versa.
  • API: requireRole("nurse") and requireRole("head_nurse") guard unit, sync, shift, analytics and export routes.
  • Data scope: nurse pull returns only that nurse’s shifts and assigned active units; head pull returns unit context.
  • Registration: the server ignores a client-supplied role and always creates a nurse.

Main API areas

  • /api/auth/login, /api/auth/register, /api/me.
  • /api/units, /api/units/:id, /api/units/:id/nurses.
  • /api/sync/push, /api/sync/pull.
  • /api/shifts, /api/shifts/:id, /api/shifts/:id/summary.
  • /api/analytics/unit, /api/reviews, /api/surveys, /api/export.
Why an event log? The app records what happened as events instead of overwriting a single “current value”. That makes it possible to recompute durations, correct a timestamp without losing the original, and build a handover from stored evidence. The UI is a projection of those events.

Q&A

Questions people usually ask

Short answers you can use without opening the code.

Why are there only two roles?

The thesis scope is nurses and head nurses. Adding admin, doctor or patient roles would introduce permissions and clinical workflows outside the evaluated product.

Can a nurse see another nurse’s shift?

No. The nurse pull is scoped to the signed-in nurse. Unit-wide shift lists, analytics and exports are head-nurse screens.

Who can alter a task or write a note on an unfinished task?

Every authenticated user has a task-alteration path within the role boundary. A nurse can edit unfinished tasks and notes in the nurse’s own shift. A head nurse can edit unfinished tasks and notes from any shift detail. Every change is an append-only TASK_EDITED event. Completed and missed tasks are frozen for both roles; the head nurse still cannot start, pause, complete, miss, defer or reschedule a task.

Is the head-nurse rating a performance score?

No. It is five separate manual 1–5 ratings plus a comment and an optional support flag. The app does not average, weight, rank or publish a composite score.

What happens if the internet drops mid-shift?

The nurse keeps working. Each action is written to Dexie first and queued in the outbox. The sync chip shows pending work. When the connection returns, the queue is pushed and the server recomputes summaries.

What if the head nurse archives a unit?

It disappears from online shift choices. Historical shifts keep their unit. An already-started offline shift still syncs if the unit row exists, so the nurse’s work is not lost.

Why can tier 1–2 never be deferred?

They represent immediate or urgent work. The product rule is that an emergency may interrupt the plan, but it must not silently move critical care out of the queue. Tier 1–2 are flagged and stay visible.

Does the app use AI?

No. The rules are deterministic TypeScript: tier rules, timers, event reductions, emergency proposals and summaries. There is no model, recommendation engine or automatic clinical decision.

What data is stored about a patient?

No patient identifiers. The bed is a number plus a short nickname. The app warns users not to type names, MRNs, dates of birth or other identifiers. Free text cannot be perfectly validated, so human input remains a listed risk.

What is not verified yet?

Physical-device APK installation/opening, real nurse usability sessions, SUS/TLX results and clinical review of the demo task tiers. These are recorded as NOT VERIFIED in the evaluation file.

Why is there a separate APK if the app is on the web?

The APK is the same Next.js project built as a static export and bundled with Capacitor. It calls the Vercel API over HTTPS. There is no second API project and no server.url.
