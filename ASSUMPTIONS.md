# Assumptions

1. **One Next.js full-stack project.** The project owner overrode the original monorepo/separate-API/static-web rules. Hono runs inside a Next.js route handler; Drizzle uses Neon.
2. **APK build.** The APK is a static export of the same project. `npm run build:mobile` temporarily moves `src/app/api` out of the app tree because a static export cannot contain server route handlers, builds with `NEXT_BUILD_TARGET=mobile`, then restores the route. Capacitor 8.6 bundles `out/` and calls the Vercel API baked in at build time via `NEXT_PUBLIC_API_URL`. It does not use `server.url`.
3. **Emergency domain remains, but the bed board was removed.** The reducer and tests still support emergency pauses/deferral, but the current shift-task demo has no emergency button or bed screen. The agreed task lists include “Allocate time for emergency” and “Manage emergencies and urgent situations” as ordinary shift tasks. Tier 1–2 are never auto-deferred.
4. **Reschedule default:** the proposed planned window is the old window shifted by the actual emergency duration (both `plannedFrom` and `plannedTo`). A fixed-offset mode exists in config. No `TASK_RESCHEDULED` event is written until the nurse confirms or edits the proposal.
5. **Recurring tasks:** the next instance starts at `completion time + intervalMin` and ends at that start plus `expectedMin`. This guarantees a full interval after care is complete; the alternative (previous due + interval) would create instantly overdue work. One successor is created per completion.
6. **Shift end:** any still-open task becomes `missed` with reason `shift_end`; active segments are closed at the shift-end timestamp.
7. **Tick-only completion** (`planned → done`) is allowed with `durationRecorded=false` and contributes zero direct-care minutes.
8. **Pinning is local UI state**, not a clinical event. It is stored on the Dexie task projection and does not sync.
9. **Head-nurse screens are online-only** and show an explicit connection state. Nurse logging, timers and shift-level handover work offline.
10. **Offline login:** a previously authenticated nurse can continue logging while offline. Sync waits for a valid JWT; an expired token requires an online re-login.
11. **Survey identity:** staff `participant_code` is stored, never a patient identifier. SUS and raw TLX are the only instruments.
12. **Free-text task titles and notes are the identifier risk.** There are no bed records and no patient fields. The UI warns against patient names/identifiers, but rule-based validation cannot reliably detect a name. This remains a human-input risk and is listed in the evaluation.
13. **Demo content** (task templates, intervals, tiers) is illustrative and needs ICU clinical review.
14. **Charts:** the deployed bundle uses lightweight custom SVG/CSS charts instead of Recharts to keep the single-project build lean. The visual/interaction requirements remain.
15. **Tests:** domain tests run under Vitest (`33` passing). API tests run against a disposable local Postgres in Docker (`scripts/api-test.ts`, `56` checks). Playwright covers authentication, both one-tap demo logins, self-registration, role routing, the privacy screen, the unit-management/assignment path, nurse/head To Do/Time Log, shift-level handover and stale-shift auto-end (`13` passing). `scripts/flow-check.mjs` is a verification script rather than an isolated test because it creates a real shift; the Playwright suite is the source of evidence.
16. **Local Neon flakiness.** The Neon pooler occasionally returns `ENOTFOUND`/timeouts from this development network on a cold login. The app shows the offline/connection state and keeps nurse writes in Dexie; this is an environment limitation, not a domain rule.
17. **Deployment evidence.** The live deployment at <https://icu-tasklog.vercel.app> was observed for earlier releases. This shift-task/alarm release is verified locally with TypeScript, product-rule lint, 33 domain tests, 56 API checks, 13 Playwright tests, the web production build and a mobile static export. Live re-verification and the new APK are recorded separately after deployment; installation/opening on a physical Android device remains **NOT VERIFIED** because no device or local Android SDK is available in this workspace.
18. **Mobile API URL.** The APK has no runtime server switcher. `NEXT_PUBLIC_API_URL` is compiled in, so the APK must be rebuilt if the Vercel URL changes.
19. **Nurse self-registration.** The public signup form creates nurse accounts only; the server never trusts a client-supplied role. Head-nurse accounts remain provisioned by the study team. Registration requires connectivity, has no email verification or PIN recovery, and is open to anyone who can reach the deployment. This is acceptable for the thesis demo but would need an invite code, rate limiting and recovery before real use.
20. **Planned windows and legacy events.** Task timing moved from a single `dueAt` to `plannedFrom`/`plannedTo`. Old events that still contain `dueAt` are normalized when read: `plannedTo = dueAt` and `plannedFrom = dueAt - expectedMin`. New production demo data was regenerated after the migration.
21. **Dynamic units are implemented.** A nurse can belong to multiple units; each shift belongs to exactly one unit; tasks inherit the shift unit. Any head nurse can manage all units in this thesis demo, with `created_by` retained for audit. Unit management is online-only; the nurse's assigned active units are cached for offline shift start. Archiving removes a unit from online shift choices and preserves historical shifts; queued offline shifts still sync if the unit exists, so work is not lost.
22. **Legacy shifts stay unassigned.** Shifts created before the unit migration keep `unit_id = NULL` and remain visible under “Unassigned” in the head-nurse filters. The server accepts an offline shift if the unit still exists even when the nurse assignment changed after the cached start, protecting queued offline work.
23. **Audited task alteration.** “Every user can alter the task” is implemented within the two-role boundary. A nurse can edit title, tier, category, planned window, expected minutes and note on unfinished tasks in the nurse’s own shift. A head nurse can do the same on any shift detail, including open shifts, and on their own head-nurse tasks. Every change appends a `TASK_EDITED` event instead of rewriting prior events. Completed and missed tasks are frozen. The head nurse still cannot start, pause, complete, miss, defer or reschedule *nurse* tasks, log interruptions or finalize nurse handovers. If a nurse and head nurse edit the same task concurrently, the reducer applies events in timestamp order; the latest event wins. There is no three-way merge in this demo.
24. **To Do and Time Log are different.** To Do is a future planned window (`plannedFrom`, `plannedTo`, `expectedMin`). Time Log is a past actual interval (`startedAt`, `endedAt`, optional note) stored as `TASK_TIME_LOGGED`. Manual To Do creation rejects a start more than five minutes in the past. Time-only input resolves on the shift start date; an end at or before the start rolls to the next day for overnight shifts. A time log marks the task done, sets `durationRecorded=true`, and adds the actual minutes to the duration summary. A second time log is rejected, as is a log for a missed task or a task with a live/paused timer. A tick-only completed task can receive a time log later.
25. **Shift-level tasks and head-nurse shifts.** The app now uses only the agreed lists: a nurse shift creates exactly 12 staff-nurse shift tasks; a head-nurse shift creates exactly 14 head-nurse tasks. All tasks have `scope = shift` and no `bedId`. There are no bed templates, bed rows or bed screens; `/beds` redirects to `/tasks`. Handover is one shift-level snapshot with the synthetic id `shift`. Head-nurse shifts are excluded from nurse analytics, reviews and CSV export. Head-nurse task management is online-only; the nurse offline Dexie/outbox flow is unchanged. Head nurses still cannot execute nurse tasks.
26. **Template refresh.** Task templates now carry `role` and `scope`. Dexie stores a local template version; when the bundled version changes, templates are replaced without deleting user shifts, tasks or events. The database migration adds the new columns with defaults so legacy rows remain valid.
27. **Shift length limit.** A shift is capped at 16 hours, treated as two normal 8-hour shifts. A stale nurse shift auto-ends when any authenticated app shell loads; a stale head-nurse shift is auto-ended when the head-nurse shift list is read or a new head shift is started. The end timestamp is capped at `startedAt + 16h`, open tasks are marked missed with reason `shift_end`, and the summary is stored at that capped time. This prevents a 49-hour active shift from remaining on the clock.
28. **APK evidence for this release.** The older APK from run `45316708579` was built from `2582d47`. The current shift-task/alarm release has not yet produced a new APK in this workspace. On-device behaviour is **NOT VERIFIED**.
29. **Foreground alarm only.** The alarm uses the Web Audio API and `navigator.vibrate` where supported. It rings once per task when an open task reaches `plannedTo`, with a persistent overdue badge as the visual fallback. Audio must be unlocked by a user gesture, so the app unlocks it on the first tap or key press and exposes **Test alarm** in **Me**. It does not ring when the app is closed; background notifications/push remain out of scope.
30. **One-tap demo login is a demo affordance.** The two buttons submit the seeded demo credentials (`amina/1111`, `head/9999`) and are not a security boundary. Manual login and nurse self-registration remain available.
31. **Demo data reset.** Because there are no real users, the production demo database was re-seeded with 26 templates, non-simulated shifts were removed, and 14 deterministic simulated shifts were regenerated with shift-level tasks and `shift` handovers. No bed rows remain.
